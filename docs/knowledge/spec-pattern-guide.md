# 3パターン設計書ガイド(V3-WIK-22)

> 目的: 知識の属人化を完全に消し(「本人しか知らない」が存在しない)、誰でも短時間で
> 「わさおレベルの理解」に到達できる状態を作る。

## 方針

全コンポーネント(機能・API・仕組み)の設計書は、以下の **3 パターン** を必須とする。
**最初に Engineer Spec を作成し、そこから他 2 パターンを派生させる**(逆順=先に平易な説明を
書いてから技術版を書く、は禁止 — 技術的正確性が平易化の過程で失われる事故を避けるため)。

| パターン | 想定読者 | 内容 | 派生元 |
|---|---|---|---|
| **Engineer Spec**(技術/開発者向け) | 実装者・レビュアー | 型定義・route・データフロー・不変条項。既存コードとの対応関係を明記 | (最初に作る・派生元なし) |
| **Human 版** | 非エンジニア(企画・運営・利用者) | 専門用語を避け、「何が・なぜ・どう変わるか」を平易語で説明。図や比喩を使ってよい | Engineer Spec から要約・平易化 |
| **AI最適化版** | LLM/エージェントが読んで実装・レビューに使う版 | 決定論的な事実のみを列挙(あいまいな形容詞を避ける)。file:line 参照・関数名・不変条項をそのまま引用 | Engineer Spec からコピー主体(要約しすぎない) |

## 適用範囲と現状(誇張ゼロ)

- 本ガイドは**執筆規約**であり、既存の全コンポーネントへ遡って3パターンを整備する作業
  そのものは含まない(その作業は各コンポーネントの担当レーンが今後の設計文書作成時に
  本ガイドへ従うことで段階的に満たされる)。
- 既存の `docs/planning/c8/design-v3-sec-45-sandbox-boundary.md` は Engineer Spec 相当の
  形式(要件再掲→実装範囲→実装していない部分の明示→引継ぎ)を既に踏襲しており、本ガイドは
  この既存パターンを一般化・明文化したものである(reuse-first、新しい書式の発明ではない)。

## 「わさおレベルの理解」の運用上の定義

Human 版だけを読んで、以下 3 点に答えられる状態を最低ラインとする:

1. これは何をするものか(1〜2文)
2. なぜ必要か(解決する困りごと)
3. 使う/触ると何が起きるか(利用者視点の結果)
